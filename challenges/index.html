Five things to build

The lessons tell you the answer and then ask you to watch it happen. These do not. Each one is a scenario with acceptance criteria and a test suite you have to turn green — the answer is not written down anywhere.

4 auto-graded · 1 open · 37 assertions in total

Every challenge is a directory with two files. starter.ts is yours to fill in. verify.ts is the acceptance criteria, executable:

npm run challenge                                        # all five
node --test challenges/01-dont-crash-at-2am/verify.ts    # just one

They fail until you make them pass. That is the point — a failing assertion that names what it wanted is a better teacher than a paragraph telling you in advance.

Read the brief, not the tests. You can open verify.ts, and sometimes you will have to. But the briefs below are written to be enough, and working from the scenario rather than the assertions is the part that resembles real work.

Challenge 01 · Don't crash at 2am

01

The scenarioGraded

Your recipe tool is running on a tablet in a café kitchen. At 2am the overnight prep list asks for a fifteen-ingredient feast, the reply runs past the token cap, and the app dies with a SyntaxError in front of nobody who can fix it. You are asked to make it never do that again.

Build: decide(reply, cap, attempt, maxAttempts) — a pure function returning parse, retry or give-up.

It must:

  • Never attempt to parse a reply that stopped early.
  • Give a truncated reply more room on retry — a retry that changes nothing is just a slower failure.
  • Never ask for more than HARD_CAP tokens, however many times it truncates.
  • Distinguish "ran out of room" from "came back malformed" from "the model was unloaded". They do not deserve the same response.
  • Terminate. Always. There is a test that runs your function in a loop and fails if it never stops.
  • Explain itself when it gives up.

Builds on Lesson 03. ~30 minutes.

Challenge 02 · The filter that missed

02

The scenarioGraded

A coeliac customer reports being served something with soy sauce in it. The recipe went through the gluten filter and came out clean. You check, and find the model had written "Soy Sauce" with two spaces — and the filter's word-boundary regex never matched. This is a real bug in this repo, and it is live right now.

Verify the bug first:

node --input-type=module -e 'import {GLUTEN_RE} from "./01-gluten-free-chef/chef.ts";
console.log(GLUTEN_RE.test("soy  sauce"), GLUTEN_RE.test("Soy-Sauce"))'

Both print false. Models write names inconsistently, and a safety filter that depends on exact spacing is not a safety filter.

Build: canonicalName(raw) and containsGluten(rawName).

It must:

  • Treat "soy sauce", "Soy Sauce", "Soy-Sauce" and "soy_sauce" as the same thing.
  • Keep catching everything the current filter catches.
  • Keep not flagging buckwheat, maltodextrin or tamari — the false positives the current regex was carefully written to avoid.
  • Trust an explicit label: "gluten-free breadcrumbs" is not a gluten ingredient. The repo's Caveats section admits this false positive; here you fix it.
  • Not be fooled by "wheat flour (not gluten free)".

This is the one with real-world stakes attached, and it is also the one where passing the tests is not the same as being safe. When you are done, write one sentence for the exercise's Caveats about what your filter still cannot catch.

Builds on Lesson 07. ~40 minutes.

Challenge 03 · Fit the brief in the budget

03

The scenarioGraded

Product have been using the tool and want six more things on every recipe: cuisine, difficulty, prep time, cook time, allergens, and the equipment needed. They also want the first recipe on screen faster than it is now. Both, please.

Build: the BriefedRecipe Zod schema.

It must:

  • Keep everything the recipe already carries — title, servings, ingredients, steps.
  • Add all six new fields.
  • Use enums wherever the value comes from a known set. Free text where a list would do is a bug here, not a style preference.
  • Contain nothing the code could derive. Total time is prep plus cook; asking the model for it buys you a chance of it being wrong.
  • Stay within 2 levels of nesting and 16 leaf fields. Both budgets come from Lesson 05's measurements, where a deep schema cost 4× the tokens and then failed.
  • Actually validate a plausible recipe.

Builds on Lesson 05. ~30 minutes.

Challenge 04 · Know when to stop

04

The scenarioGraded

A support note: "it thinks for thirty seconds and then gives me the same wrong answer it had at the start." You watch the log. Attempt one is 0.5 off target, attempt two 0.2, attempt three back to 0.5. It is cycling — fixing the protein breaks the calories, fixing the calories breaks the protein — and the fixed count of three attempts means it pays for all of it before giving up.

Build: shouldContinue(distances, maxAttempts), given how far from target each attempt landed.

It must:

  • Continue while there is meaningful progress — at least MIN_IMPROVEMENT relative to the attempt before.
  • Stop when progress stalls. Half a percent is noise, not improvement.
  • Stop when the answer gets worse.
  • Stop when it oscillates, rather than cycling forever between two bad answers.
  • Stop at zero. The target was hit.
  • Respect maxAttempts as an absolute ceiling.

Builds on Lesson 07. ~25 minutes.

Challenge 05 · The café board

05

The scenarioOpen

The café wants a prep-list tool. The chef types what is in the walk-in fridge — in a hurry, with typos, sometimes just "chicken, rice, whatever greens" — and gets back a prep list for the day. It runs on one laptop in the back office. It must not crash, it must not quietly invent an allergen, and when it is unsure it has to say so rather than guess.

There is no right answer to this one and no test that can check your judgement. What the verifier checks is that you shipped it the way this repo ships things: a real exercise directory, a README with honest Caveats, tests that run without a model, and the logic pulled out where tests can reach it.

The constraints that make it realistic:

  • Hostile input. The chef is busy. Empty strings, typos, one-word answers, nonsense. None of it may crash the tool.
  • A latency budget. Something useful on screen within a few seconds. You know from Lesson 08 that this is mostly a question of streaming and warm-up, and from Lesson 05 that schema shape decides the rest.
  • One laptop. 24 GB, shared with everything else the office runs. Lesson 04 is the arithmetic.
  • Honest uncertainty. When the model's output fails your checks, the tool says so. Never present a verified-wrong value as if it were fine.

Grade yourself on these — they are the questions I would ask:

  1. What exactly does code decide, and what does the model decide? Can you state the seam in one sentence?
  2. What happens on the worst input you can think of? Have you actually tried it?
  3. What does your Caveats section admit? If it admits nothing, it is not finished.
  4. Could someone else run it from your README alone?

Builds on everything. A few hours. This is the exercise-02 candidate from Lesson 09, made concrete.
