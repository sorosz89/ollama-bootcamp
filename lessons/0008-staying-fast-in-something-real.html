Ollama Bootcamp · Lesson 08 · Running the model well

Staying fast in something real

A model that is fast enough at the command line can feel broken in an application. The difference is mostly about when the user sees the first character, and what happens when two people ask at once.

Part 1 ~6 minutes · Part 2 ~11 minutes · 26 Oct 2026

Everything so far has measured one call at a time, by hand. This lesson is what changes when the model sits behind something other than you.

Part 1

The idea

Perceived speed and actual speed are different problems. One of them you can fix today.

Waiting is worse than slow

Your exercise waits for the complete reply and then prints it. For a 482-token recipe at ~50 tokens a second, that is roughly ten seconds of nothing, then everything at once.

Stream the same call and the first words appear in well under a second. The total time is identical — the model is doing exactly the same work at exactly the same rate — but the experience is transformed, because the wait is filled rather than empty.

The keystone

Streaming does not make generation faster. It makes the time to first token the number the user feels, instead of the time to last token. That is usually a tenfold improvement in perceived speed for free.

The two waits you can actually remove

WaitCauseFix
~3.4 s before anything, occasionallyCold start — the model was unloaded after 5 minutes idle.Keep it resident: keep_alive: "30m", or warm it at startup.
~10 s before anything, every timeYou are waiting for the whole reply before showing any of it.Stream.

Both measured on this machine in Lesson 02. Neither requires a better model or a faster laptop.

Streaming, in the client you already use

const stream = await ollama.chat({
  model: MODEL,
  messages: history,
  stream: true,
});

let full = "";
for await (const part of stream) {
  process.stdout.write(part.message.content);   // appears as it arrives
  full += part.message.content;
}
// `full` is the complete reply; the final part carries the timing fields.

One flag and a loop. The pieces arrive as the model produces them.

Streaming and structured output pull against each other. A partial JSON string is not parseable, so you cannot validate until the stream completes — and you certainly cannot show a half-finished object to a user as if it were a result. For chef.ts, streaming the text of a recipe is lovely; streaming a schema-constrained recipe mostly means watching JSON punctuation appear. This is a real tension, not a detail, and it is the main reason your exercise does not stream today.

Do it: feel the difference

  1. Compare the two experiences directly, without touching your exercise:

    ollama run qwen3.5:9b "Write a 200-word description of a gluten-free traybake."

    That streams by default. Note how quickly text starts.

  2. Now the same request without streaming:

    curl -s http://localhost:11434/api/generate -d '{"model":"qwen3.5:9b","prompt":"Write a 200-word description of a gluten-free traybake.","stream":false}' | head -c 200

    Same work, same total time, completely different feel.

  3. Warm the model deliberately and watch the cold start disappear:

    curl -s http://localhost:11434/api/generate -d '{"model":"qwen3.5:9b","keep_alive":"30m"}' > /dev/null
ollama ps

    Check the UNTIL column. An empty prompt with a keep_alive loads the model without generating anything — the standard warm-up trick.

If you remember only this
  1. Stream whenever a human is waiting. Same total time, a tenth of the perceived wait.
  2. Warm the model at startup and keep it resident, so no user pays the 3.4-second cold start.
  3. Streaming fights structured output. You cannot parse half an object — decide which you need.
Part 2

More than one request at a time

What Ollama does under concurrency, what it costs in memory, and how to cancel work nobody is waiting for.

By default, one at a time

Ollama queues. For a given model, the number of requests it will process simultaneously is OLLAMA_NUM_PARALLEL, and the default is 1. (FAQ) Everything else waits its turn, up to OLLAMA_MAX_QUEUE (default 512), after which the server returns a 503. (FAQ)

This is a reasonable default and an unpleasant surprise. Two users of your tool do not halve each other's speed — the second one waits for the first to finish entirely, then starts.

You can raise it, but the price is stated plainly in the docs:

"Required RAM will scale by OLLAMA_NUM_PARALLEL × OLLAMA_CONTEXT_LENGTH", and "parallel request processing for a given model results in increasing the context size by the number of parallel requests. For example, a 2K context with 4 parallel requests will result in an 8K context and additional memory allocation." (FAQ)

So on this machine — 7.6 GB of weights in roughly 18 GB of usable memory — four parallel requests at a 4k context means allocating as though you had a 16k context. That is affordable. Four parallel at a 64k context is not. Concurrency is bought with the memory budget from Lesson 04, and overspending puts you back on the CPU cliff.

VariableDefaultRaise it when
OLLAMA_NUM_PARALLEL1Several users share one model and you have memory spare.
OLLAMA_MAX_LOADED_MODELS3 per GPUYou genuinely need different models resident at once.
OLLAMA_MAX_QUEUE512Rarely. Hitting it means you needed a queue of your own.

Cancelling work nobody wants

A user closes the tab, or types a new question before the last one finished. Without cancellation the model keeps generating into the void, holding the one parallel slot everyone else is queued behind.

The JS client returns an abortable iterator from a streaming call:

const stream = await ollama.chat({ model, messages, stream: true });

// elsewhere — user navigated away, or asked something new
stream.abort();

// or, to stop every in-flight request on the client
ollama.abort();

In an interactive tool this is not a nicety. One abandoned 48k-token prefill — measured at two minutes in Lesson 02 — is two minutes nobody else can use the model.

Memory knobs for a long-running process

A model left resident for days behaves differently from one you poke at the command line:

  • keep_alive: -1 pins it forever. Good for a dedicated machine, antisocial on a laptop you also work on — it will hold several gigabytes until the server restarts.
  • Flash attention is used automatically where supported, and OLLAMA_FLASH_ATTENTION=1 forces it on. It "significantly reduces memory usage as the context size grows". (FAQ)
  • OLLAMA_KV_CACHE_TYPE quantizes the conversation cache, default f16, and needs flash attention to help. It is global — every model on the server is affected. (FAQ)

A checklist before you ship anything

  1. Warm the model at startup so the first real user does not pay the cold start.
  2. Stream if a human is waiting, unless you need to validate the whole object first.
  3. Cancel on disconnect. Hold the abort handle somewhere you can reach it.
  4. Set num_predict deliberately — Lesson 03 — so a runaway generation cannot hold the slot indefinitely.
  5. Decide your concurrency and check it fits in memory before raising OLLAMA_NUM_PARALLEL.
  6. Watch ollama ps under load. The PROCESSOR column is still the first thing to check when something is slow.

Do it: make the exercise stream

  1. Add a streaming path to chef.ts that prints the raw JSON as it arrives, accumulating it into a string. Parse and validate only once the stream ends.

  2. Decide honestly whether it improved anything. Watching schema-constrained JSON stream is not obviously better than a short wait — a well-argued "no" is the right answer if that is what you find, and belongs in the exercise's Caveats.

  3. Warm the model when chef.ts starts, with an empty prompt and a keep_alive. Measure the first recipe before and after.

  4. Wire up Ctrl-C to abort() the in-flight request rather than killing the process mid-generation.
