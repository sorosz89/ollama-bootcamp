Ollama Bootcamp · Lesson 07 · Making the output trustworthy

What to verify, what to re-ask

Every lesson so far has pointed at the same seam: the model produces, code checks. This one is about drawing that line deliberately — which errors code should fix silently, which are worth sending back, and which mean you should stop.

Part 1 ~6 minutes · Part 2 ~10 minutes · 26 Oct 2026

check() in your exercise is a good instance of a general pattern. This lesson extracts the pattern so you can apply it to the next exercise without re-deriving it.

Part 1

The idea

Sort every possible error into three buckets. The bucket decides the code you write.

Three buckets

BucketExampleWhat to do
Code can fix itIngredient name is " Chicken Breast " with stray spacing and capitals.Fix it silently. Never spend a model round-trip on something a trim() solves.
Only the model can fix itThe recipe contains couscous, and the dish needs rethinking without it.Send it back, with the specific problem stated.
Nobody can fix it600 kcal at 90 g of protein from a cucumber salad.Stop. Report honestly. Retrying cannot help.
The keystone

A retry is only worth making if something about the request has changed and the model is capable of doing better. If either is false, you are burning seconds to arrive at the same answer.

The bucket most people get wrong

It is the first one. There is a strong pull toward sending everything back to the model, because the feedback loop feels like the clever part of the system. But every round-trip costs a prefill plus a full generation — measured in Lesson 02 at several seconds for a recipe — and a round-trip that fixes capitalisation is pure waste.

The test is simple: could you write the fix as a deterministic function? If yes, write it. Normalising, rounding, sorting, deduplicating, unit conversion, formatting — all code. The model's judgement is expensive; spend it only on judgement.

Writing a problem the model can act on

When something does go back, the quality of the message decides whether the retry works. Your exercise does this well, and it is worth seeing why:

// Weak — true, but not actionable
"The macros are wrong."

// Strong — what, by how much, and in which direction
"protein per serving is 38 g, target 45 g."

Three properties make the difference: it names which field, it gives the actual and the wanted value, and it is per serving — the same unit the model was asked to work in. A model cannot act on a complaint it has to interpret.

Do it: audit your own check

  1. Open check() in 01-gluten-free-chef/chef.ts. For each problem string it can produce, decide which of the three buckets it belongs in.

  2. Find a case in bucket one — something code could just fix. (Hint: look at how ingredient names are matched against the gluten list, and what happens with stray whitespace or capitalisation.)

  3. Find the bucket-three case. What does the exercise currently do when it is unsatisfiable after three attempts? Is that the right behaviour?

  4. Write one sentence describing where you would draw the line, then compare it with Part 2.

If you remember only this
  1. Three buckets: code fixes it, model fixes it, nobody fixes it.
  2. If a deterministic function could fix it, write the function. Don't spend a round-trip.
  3. Feedback must name the field, the actual value and the target. Vague complaints do not converge.
Part 2

Loops that converge, and knowing when they won't

Why a retry loop can oscillate forever, and how to notice before your user does.

Fixing one thing breaks another

Run the cucumber-salad experiment from Lesson 01 and watch the retry log closely. A pattern shows up: the model raises the protein, which pushes the calories over; you complain about calories, it cuts the oil, which drops the fat below target. The constraints are coupled, and fixing them one at a time can cycle.

Three defences, in increasing order of effort:

  • Send all problems at once, not the first one. Your exercise already does this — problems.join(" ") — and it matters more than it looks, because it lets the model trade off between constraints instead of chasing them serially.
  • Say which constraint dominates. "Calories matter most; get within 10% of the macros if you can" gives the model a way to resolve the conflict, instead of guessing which one you care about.
  • Detect the oscillation. If attempt 3's problems are the same set as attempt 1's, the loop is not converging and a fourth attempt will not help either.

Measuring convergence rather than hoping

A retry loop deserves one number: is the total error going down?

const distance = (tot: Macros, goal: Macros) =>
  Object.keys(goal).reduce((d, k) =>
    d + Math.abs(tot[k] - goal[k]) / goal[k], 0);

// after each attempt
if (attempt > 1 && distance(tot, goal) >= previousDistance * 0.95) {
  // Not meaningfully closer. Another round is unlikely to help.
  return { kind: "off-target", recipe, problems };
}

This turns "three attempts" from a superstition into a policy: keep going while you are making progress, stop when you are not. It usually runs fewer attempts than a fixed count, and gives up for a reason you can print.

Why 0.95 and not 1.0

Because a model will often produce a trivially different answer that is a fraction of a percent closer, forever. Requiring meaningful improvement — say 5% — stops the loop treating noise as progress. The exact threshold is arbitrary; having one is not.

The honest failure

Some requests are impossible, and the system's job is to say so clearly. Your exercise currently prints the recipe with (still off target) appended, which is a defensible choice: a near-miss recipe is still useful, and the caveat is visible.

What makes it defensible is that the caveat is specific and honest. Compare the options:

On final failureVerdict
Print the recipe silentlyWrong. The user believes numbers that are known to be false.
Print it with (still off target)Acceptable. Honest, though it does not say by how much.
Print it with the actual gap: "protein 38 g, wanted 45 g"Better. The user can judge whether it matters to them.
Refuse and explain why it is impossibleBest when it really is impossible — but you have to be sure, and usually you are not.

The general rule, and the one that matches this repo's attitude in its Caveats sections: never let a verified-wrong value out without the verification result attached to it.

Generalising the pattern

For any new exercise, the same four questions produce the design:

  1. What can code decide with certainty? Arithmetic, membership in a list, format, ordering. That is your check().
  2. What needs judgement? That is what the model is for, and the only thing worth a round-trip.
  3. What does a useful complaint look like? Field, actual, target, in the model's own units.
  4. What happens when it does not work? Decide this before writing the loop, not after it bites.

Answer those four and the structure writes itself — which is the real reason the exercises in this repo all look alike.

Do it: upgrade the loop

  1. Add the distance() function to chef.ts and log it after each attempt. Run the cucumber-salad case and watch whether it falls.

  2. Replace the fixed three attempts with "stop when not improving", keeping three as a hard upper bound.

  3. Upgrade the final message from (still off target) to name the remaining gaps.

  4. Move one bucket-one problem out of check() and into a normalisation step before checking. Confirm the tests still pass — and add one for the normaliser, since it is pure and needs no model.
