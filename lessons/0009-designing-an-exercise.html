Designing an exercise from a finding

The mission was never "learn about Ollama". It was to build a series of small exercises sharp enough to survive scrutiny. This lesson is the one that produces them.

Part 1 ~7 minutes · Part 2 ~10 minutes · 26 Oct 2026

By now you have a pile of measurements, a corrected assumption or two, and several things that surprised you. This is how one of those becomes exercise 02.

Part 1

The idea

An exercise is not a demo. It is one surprise, made reproducible.

What makes an exercise worth publishing

The test is narrow: does someone who works through it end up believing something they did not believe before? A demo shows that a thing can be done. An exercise changes what the reader expects.

Exercise 01 passes because of one sentence: the LLM writes, Python checks — now TypeScript checks. A reader who has not met that split assumes the model should be able to do arithmetic, watches it fail, and leaves with a different model of what these systems are for.

The keystone

Start from the surprise, not the topic. "Structured output" is a topic. "The schema is enforced mechanically, so the shape is guaranteed and the numbers are still invented" is a surprise — and only the second one can be built into something.

Your candidate surprises

Everything below came out of this course, measured on your machine. Each is a potential exercise:

FindingFromWould make an exercise about…
A reply can hit the token cap and still be valid JSON up to that point03Failure handling — the one that fixes a real bug, so it has a built-in motive.
A nested schema cost 4× the tokens and then failed outright05Schema design as a latency and reliability decision.

The third and fourth are the most interesting and the hardest to build, because their conclusions are "it depends" and "nothing happened". Those are true and valuable, and they are also difficult to wrap a satisfying exercise around. The first is the easiest and the most useful.

The shape every exercise here follows

From the repo's own CLAUDE.md, which you can now read as a specification:

  • One directory, NN-exercise-name/, holding a README, one script, and a test file.
  • The model generates, code verifies, problems feed back, retries are bounded.
  • Tests cover the pure functions only. No mocked Ollama, no model under test — which forces the interesting logic out of the I/O path, where it is testable anyway.
  • A README with the lesson in one line, a mermaid diagram of the loop, Run / Steps to learn / Stretch goals / Caveats.

The constraint that does the most work is the testing rule. "No Ollama in tests" sounds like a CI convenience; in practice it forces you to separate judgement from verification, which is the whole pedagogical point.

Do it: pick one

  1. Choose a finding from the table — or a better one of your own.

  2. Write the one-line lesson first, before any code. If you cannot state it in a sentence, the exercise is not ready.

  3. Write the Caveats section second. What will this exercise not prove? Naming that early stops the exercise overclaiming later.

  4. Only now write the script. If the one-liner and the caveats are right, the code is mostly obvious.

If you remember only this
  1. Start from a surprise, not a topic. If nothing surprised you, there is no exercise yet.
  2. Write the one-line lesson and the caveats before the code.
  3. Keep the model out of the tests. It forces the design that makes the lesson legible.
Part 2

Working one through

Exercise 02, designed end to end, so the next one is mechanical.

The candidate: a schema budget

Taking the Lesson 05 finding, because it is measurable, surprising, and nobody writes about it.

One-line lesson: the shape of your schema is a latency and reliability decision, and you can measure it in seconds.

The seam: the model fills schemas; code measures what each shape cost and decides whether it was worth it. Same split as exercise 01, applied to the request rather than the reply.

What the reader does: runs the same prompt through three schema shapes, sees the token counts diverge, watches the nested one fail, then flattens it and watches it recover.

What the pure functions are

This is where the design gets decided, because it is what the tests can reach:

FunctionPure?Test
schemaDepth(schema) — how deeply nestedYesKnown schemas, known depths.
estimateFields(schema) — leaves to be filledYesFlat vs nested counts.
verdict(tokens, cap, doneReason) — ok / truncated / expensiveYesTable of cases, including the boundary.
runCase(schema, prompt) — the actual callNoNot tested. Keep it thin.

Three pure functions, one thin I/O wrapper. The tests run in milliseconds with no model, and the reader can see exactly which decisions are deterministic.

The README, in order

  1. One line: "Schema shape is a latency decision. The same recipe, three shapes: 290 tokens, 332 tokens, or a failure."
  2. Mermaid diagram: prompt → three schemas → three measurements → a verdict table.
  3. Run: the command, and which model it assumes.
  4. Steps to learn: run it; predict the nested result before looking; flatten it; re-run.
  5. Stretch goals: add a fourth shape; try it on a smaller model; measure whether one nested call beats three flat ones.
  6. Caveats: one model, one machine, one prompt. Token counts vary run to run. A nested schema that fits comfortably is not slow because it is nested — it is slow because it is long.

That last caveat matters: it is the honest version of the finding, and without it the exercise teaches a superstition rather than a measurement.

The traps

TrapLooks likeFix
Teaching two things"…and while we're here, let's also cover streaming."Two lessons. The reader's working memory is the binding constraint.
Overclaiming"Nested schemas are slow.""On this model, this prompt, this machine, nesting cost 4×."
Untestable designAll the logic inside the API call.Pull the decisions into pure functions. The rule forces the design.
A demo, not an exerciseReader runs it, says "neat", learns nothing.Make them predict before they run. A wrong prediction is the lesson.

The prediction step is the cheapest quality improvement available. "Guess which one fails before you run it" converts passive reading into a test the reader gives themselves — the same reason every lesson here has a quiz.

Do it: build exercise 02

  1. Create 02-schema-budget/ with a README, a script and a test file.

  2. Lift the three schemas from assets/schema-bench.ts — the measuring is done; this is about shaping it into a lesson.

  3. Write the three pure functions and their tests first. Confirm npm test still passes without Ollama running.

  4. Add the row to the README index table and the 02 script to package.json, as CLAUDE.md requires.

  5. Reread your Caveats section as a sceptic. If any sentence claims more than you measured, cut it.
