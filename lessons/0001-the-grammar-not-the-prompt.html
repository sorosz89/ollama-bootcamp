The grammar, not the prompt

Your chef.ts already passes a JSON schema to Ollama. It is not asking the model nicely — it is making every other answer physically unsamplable. Knowing exactly where that guarantee stops is the whole lesson.

~12 minutes · Ollama running, qwen3.5:9b · 26 Oct 2026

You already know cloud structured output: you hand OpenAI or Anthropic a schema, and a valid object comes back. The mental model most people carry over is the provider validates the reply and retries until it fits. That model is wrong for Ollama, and the difference is the reason check() exists in your repo.

The keystone

format does not ask the model for JSON. It deletes every token that would break your schema before the model is allowed to pick one.

The mechanism, in one pass

When you pass a schema rather than the string "json", Ollama compiles it into a GBNF grammar — the grammar format llama.cpp uses — and installs it in the sampler. At every single token, the model produces its usual distribution of candidates, and then the grammar crosses out the ones that would make the output invalid so far. The model samples from what survives. (Clayton, 2026)

So the shape is not a request that might fail. It is an invariant of the decoding loop. A missing fat_g, a stray apology before the opening brace, a trailing markdown fence — none of them are reachable states.

This also explains the throughput cost people report: the masking step runs per token and is not parallelised, so a complicated schema can noticeably slow generation. (Clayton, 2026) Your Recipe schema is small, so the cost is small.

Three things it still will not give you

The guarantee is narrow, and every gap in it is already defended somewhere in chef.ts. This table is the part worth remembering.

GapWhat goes wrongYour defence
Truth The grammar enforces that protein_g is a number, never that it is the right number. A 9B model will cheerfully invent 45 g of protein in a cucumber. check() recomputes the macros and feeds the discrepancies back as a revision message.
Completion Ollama does not validate the finished reply against the schema. If generation stops early — token limit, context exhausted — you get well-formed-so-far JSON with no closing braces, and JSON.parse throws. (Clayton, 2026) Nothing yet. Recipe.parse(JSON.parse(…)) will throw and kill the run. A real gap in exercise 01.
Quality If the prompt never mentions JSON, the grammar forces a shape the model was not heading towards, so sampling happens far down the distribution: padding, whitespace, listless content. Ollama's own docs say to "instruct the model to use JSON in the prompt. Otherwise, the model may generate large amounts whitespace." (Ollama API docs) Your system prompt ends with "Answer only in the requested JSON." — which now stops looking redundant.

The reframe: constrained decoding moves work, it does not remove it. It takes parsing off your plate entirely and leaves verification wholly on it. That seam — model writes, code checks — is the thing your bootcamp is really teaching.

Do it: make the model lie to you

Five minutes in the terminal. The point is to see perfectly-shaped JSON carrying nonsense, and watch the feedback loop catch it.

  1. From the repo root, start the chat and give it targets a vegetable cannot meet:

    npm run 01
# Calories per serving: 600
# Protein/Carbs/Fat %: 60/20/20
# What do you feel like? > a simple cucumber and lettuce salad

    That asks for 90 g of protein out of salad leaves.

  2. Watch the retry log. You should see attempt 1: fixing -> lines quoting real arithmetic. Note which problem the model fixes first, and whether fixing one breaks another.

  3. Look at what never happens. No malformed JSON. No "Sure! Here's a recipe:" preamble. No markdown fence. Every attempt parsed cleanly on the first try — that is the grammar, silently doing its job while the content is wrong.

  4. If it survives three attempts still off target, you get (still off target) and the recipe prints anyway. Ask yourself: is printing a wrong answer the right behaviour for exercise 01? There is a defensible case either way — have the argument before you change it.

  5. Optional, and it may not reproduce on every model: delete the sentence "Answer only in the requested JSON." from SYSTEM in chef.ts, re-run, and look for thinner steps or padded strings. Put it back afterwards. Qwen is well-behaved enough that you may see no change at all — a null result here is still worth knowing.
