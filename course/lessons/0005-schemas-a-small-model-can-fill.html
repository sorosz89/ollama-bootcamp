Schemas a small model can fill

The grammar will force a model into any shape you define. That does not mean every shape is a good idea. Schema design turns out to be a latency decision and a reliability decision, not just a modelling one.

Part 1 ~6 minutes · Part 2 ~10 minutes · measured on this machine, 26 Oct 2026

Lesson 01 established that the schema is enforced mechanically. The obvious next move is to put everything in the schema — deep structure, rich objects, every field you might want. This lesson is about why that backfires, with numbers.

Part 1

The idea

Every field in your schema is tokens the model has to write. Tokens are time, and time has a ceiling.

A schema is a bill

When you ask for a nested object with twelve fields, the model does not just "fill it in". It has to generate every brace, every key name, every quote mark, one token at a time, at the decode speed from Lesson 02 — around 50 tokens a second here.

Structure is not free. {"recipe": {"meta": {"title": … spends tokens on punctuation and key names before any actual content appears. A flat object spends them on content.

The keystone

The same request, asked for in three different shapes: 290 tokens flat, 332 with enums, and over 1,200 deeply nested — where the nested version ran out of room and failed entirely. Shape is not cosmetic.

The three shapes, measured

One prompt — "a gluten-free chicken traybake for two" — asked for three ways on this machine:

SchemaTokens generatedTimeResult
Flat — title, ingredients, steps2905.3 sParsed cleanly
Flat + enums — adds difficulty, meal type3326.5 sParsed cleanly
Deeply nested — recipe → meta / components → items → quantity + macros1,200 (capped)19.4 sTruncated and failed

Four times the tokens, four times the wait, and then nothing usable — it hit the generation cap mid-structure and became the exact failure from Lesson 03. Deep nesting did not make the answer richer. It made it absent.

Three rules that follow

  • Flatten by default. Two levels of nesting is usually plenty. If you find yourself writing a.b.c.d, ask whether the model needs to express that, or whether your code can assemble it afterwards from something flatter.
  • Prefer enums to free text where the answer is from a known set. An enum costs a handful of tokens, cannot be misspelled, and needs no validation — the grammar guarantees it. The measured cost of adding two enums was 42 tokens.
  • Ask only for what you consume. Every field you do not read is pure latency. This sounds obvious and is routinely ignored, because adding a field to a schema feels free when you write it.

Do it: measure your own schema

  1. Run the comparison yourself:

    node course/assets/schema-bench.ts

    Three shapes, same prompt. Note the token counts, and watch the nested case fail.

  2. Open 01-gluten-free-chef/chef.ts and look at the Recipe schema with this in mind. It is two levels deep — a recipe with an array of ingredient objects — and every field is consumed by check() or printed. That is a well-shaped schema, and now you know why.

  3. Try making it worse. Wrap it in an outer object, or split grams into { amount, unit }, and re-run npm run 01. Compare how long the first recipe takes to appear.

  4. Put it back.

If you remember only this
  1. Every field costs tokens, and tokens cost seconds. Schema design is latency design.
  2. Deep nesting is the expensive kind of structure. Measured here: 4× the tokens, and it failed.
  3. Enums are cheap and self-validating. Use them wherever the answer comes from a known set.
Part 2

What the grammar can and cannot express

Where JSON Schema features stop being enforceable, and how to design around the gap.

Constraints the grammar enforces

The schema becomes a grammar, and a grammar is about syntax. So it enforces exactly the things that are structural:

Enforced mechanicallyNot enforced
Which keys exist, and that required ones appearThat a number is in a sensible range
That a value is a string, number, boolean, array or objectThat a string is a real ingredient and not invented
That an enum value comes from your listThat the right enum value was chosen
Nesting structure and array-nessThat an array has a sensible number of items

The pattern: anything expressible as "which characters may come next" is guaranteed; anything requiring the model to have understood the world is not. Zod constraints like .min(1), .positive() or .email() largely live on the right-hand column — they will be checked when you parse the reply, but they do not shape generation, so a violation becomes a parse failure rather than something the model was prevented from writing.

Design consequence

This means a Zod refinement is a verification tool, not a generation tool. If a constraint matters, put it in two places: the schema, so the parse rejects violations, and the prompt, so the model is steered away from them in the first place. Belt and braces, for the same reason Lesson 01's system prompt still says "answer only in the requested JSON".

Moving structure out of the model

The nested schema failed because it asked the model to produce structure it did not need to invent. Compare the two framings of the same data:

// Expensive: the model generates the grouping
components: [
  { component: "the chicken", items: [ { name, quantity: { amount, unit }, macros: {…} } ] },
  { component: "the dressing", items: [ … ] },
]

// Cheap: the model generates facts, your code does the grouping
ingredients: [
  { name: "chicken thigh", grams: 300, group: "chicken", protein_g: 54, … },
  { name: "olive oil",     grams: 15,  group: "dressing", protein_g: 0,  … },
]

Both carry the same information. The second is flat, costs far fewer tokens, and the grouping is a two-line reduce in TypeScript — code that cannot get it wrong, unlike a model that might put the oil in the wrong group. Structure your code is capable of deriving should be derived, not generated.

This is the same seam as the rest of the repo: the model supplies the judgement (what goes in the dish, roughly how much), and code supplies the determinism (arithmetic, grouping, formatting).

When a big schema is the right answer

Not every nested schema is a mistake. Reach for one when:

  • The nesting carries real information the model genuinely decides — a tree whose shape is the answer, like an outline or a dependency graph.
  • One call beats several. Three flat calls each pay their own prefill; one structured call may well be cheaper overall. Measure rather than assume.
  • You have raised num_predict to match. A big schema with a default cap is Lesson 03 waiting to happen — the measured failure above was precisely this.

Do it: shape a schema deliberately

  1. Take the nested case in course/assets/schema-bench.ts and flatten it by hand — same information, fewer levels. Re-run and compare token counts.

  2. Raise num_predict for the nested case until it completes, and note how long it takes. That is the real cost of the shape, now that it is not failing.

  3. Replace one free-text field in your flattened version with an enum. Check the token count moves the way you expect.

  4. Write down the rule you would give someone else about when to nest. If you can state it in one sentence, it is a candidate for an exercise — see Lesson 09.
