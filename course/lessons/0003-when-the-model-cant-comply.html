When the model can't comply

Lesson 01 found a hole in your exercise and left it open: a reply that stops halfway is still perfectly valid JSON right up to the point it stops. Here is how to see it coming, and what a retry loop should do when it runs out of road.

Part 1 ~6 minutes · Part 2 ~10 minutes · measured on this machine, 26 Oct 2026

Every call to a local model has three possible endings, and your code currently handles one of them.

Part 1

The idea

Three endings, one habit to build. No new tools.

Three ways a reply ends

EndingWhat you getWho can fix it
It finishedComplete, schema-valid JSON.Nobody needs to — but it may still be wrong, which is Lesson 01's problem.
It ran out of roomJSON that is valid up to the character it stopped at, and then simply stops. No closing brace.You. Give it more room, or ask for less.
It never arrivedAn error: Ollama not running, model not pulled, request aborted.You, usually before the program runs at all.

The middle one is the interesting ending, because it does not look like a failure from the model's side. The grammar from Lesson 01 did its job perfectly: every token it emitted was valid. It simply hit a limit and stopped mid-word.

The keystone

The reply tells you how it ended, in a field called done_reason. Check how it ended before you try to parse it. A truncated reply is not a parsing problem, and catching it as one hides the real cause.

Why try/catch alone is not enough

You could wrap the parse in a try and move on. Many people do. The trouble is that the exception you catch says "Unterminated string in JSON at position 109" — which tells you the shape was broken, not why, and the two whys need opposite fixes:

  • Ran out of room → raise the limit, or shrink the request. Retrying the same call unchanged will fail the same way, forever.
  • Genuinely malformed → something is wrong with your schema or the server, and retrying might help.

Telling them apart costs one if. Confusing them costs you a retry loop that spins three times and achieves nothing.

The habit

const res = await ollama.chat({ /* … */ });

if (res.done_reason === "length") {
  // Hit the generation cap. Parsing is pointless — the reply is incomplete.
  // Raise num_predict, or ask for a smaller object.
}

const value = Schema.parse(JSON.parse(res.message.content));

Three lines, in front of every parse. That is the whole lesson in Part 1.

Do it: break it on purpose

  1. Open 01-gluten-free-chef/chef.ts and find the ollama.chat call. Add a deliberately tiny cap to its options:

    options: { temperature: 0.3, num_predict: 60 },

  2. Run npm run 01 and ask for anything. It will crash, with a SyntaxError from JSON.parse and a stack trace. That is the bug Lesson 01 predicted, reproduced on demand.

  3. Read the error. Notice it says nothing about running out of room — the symptom and the cause look unrelated, which is exactly why this one is worth knowing by sight.

  4. Put num_predict back (or delete it). Leave the bug in place for now: Part 2 fixes it properly, and it is more satisfying to fix something you have watched break.

If you remember only this
  1. A reply can stop early and still be valid JSON up to that point. The grammar cannot prevent it.
  2. done_reason tells you how it ended. "length" means it ran out of room.
  3. Check before you parse. A truncation caught as a parse error sends you hunting in the wrong place.
Part 2

Building a loop that gives up well

The measured behaviour, the three values of done_reason, and what to do on the attempt that does not work.

What truncation actually looks like

Three calls for the same recipe, with the cap set lower and lower. Measured here:

num_predictdone_reasonLast characters of the replyJSON.parse
40"length"…"ingredients": [ { "name": "ChickenUnterminated string
120"length"…"steps": [ "Preheat oven to 20Unterminated string
600"length"…"Serve immediately."Expected ',' or ']'

Note the third row. Six hundred tokens produced something that looks finished — a complete final sentence, a closing quote — and still fails, because the arrays and braces around it were never closed. You cannot eyeball this. You have to check the field.

Worth knowing

done_reason has other values. "stop" is the normal one: the model decided it was finished. "unload" appears when the model was unloaded mid-request. Only "length" means "I had more to say".

How much room does a recipe need?

From Lesson 02: a Recipe reply measured a steady 482 tokens. The default num_predict is generous enough that you will not normally hit it — which is precisely why this bug lies dormant until the day someone asks for a twelve-ingredient curry, and then it crashes in front of them.

Two defences, and you want both:

  • Set num_predict deliberately, somewhere comfortably above your measured typical reply. Guessing low is a crash; guessing high costs nothing unless the model runs away.
  • Handle the case anyway. A limit you set from one measurement is a limit someone will exceed.

A loop that terminates

Your current loop retries up to three times and then prints whatever it has. That is a reasonable policy for wrong numbers — a slightly-off recipe is still a recipe. It is the wrong policy for truncation, because there is nothing to print. The two failures deserve different handling:

type Outcome =
  | { kind: "ok"; recipe: Recipe }
  | { kind: "off-target"; recipe: Recipe; problems: string[] }
  | { kind: "no-answer"; why: string };

async function ask(history: Message[], cap: number): Promise<Outcome> {
  for (let attempt = 1; attempt <= 3; attempt++) {
    const res = await ollama.chat({ /* … */ options: { num_predict: cap } });

    if (res.done_reason === "length") {
      cap = Math.round(cap * 1.5);        // give it room and try again
      continue;                            // ← changing the request, not repeating it
    }

    let recipe: Recipe;
    try {
      recipe = Recipe.parse(JSON.parse(res.message.content));
    } catch {
      continue;                            // malformed: a retry might genuinely help
    }

    const { problems } = check(recipe, /* … */);
    if (problems.length === 0) return { kind: "ok", recipe };
    if (attempt === 3) return { kind: "off-target", recipe, problems };
    history.push(revisionMessage(problems));
  }
  return { kind: "no-answer", why: "three attempts, no complete reply" };
}

Three things make this better than a bare counter:

  1. Each retry changes something. Retrying an identical request that failed deterministically is just waiting slower. On truncation the cap goes up; on bad numbers the problems go back to the model.
  2. Giving up is a result, not an exception. no-answer is a value the caller can handle — print a message, try a smaller request, fall back. An uncaught SyntaxError is none of those things.
  3. Off-target and no-answer are distinct. One has a recipe you can show with a warning; the other has nothing. Collapsing them loses the only information the user cares about.

This is the fix for exercise 01. The current code assumes every reply parses. Making the outcome a union type, rather than "a recipe, or an exception from three stack frames down", is the change worth making — and it is a better teaching artifact, because the reader can see every ending the system has.

Do it: fix the bug

  1. In chef.ts, add the done_reason === "length" check before the parse, and raise num_predict on that branch instead of giving up.

  2. Wrap the parse so a malformed reply continues the loop instead of killing the process.

  3. Make the failure case visible: when three attempts produce nothing, print a plain sentence saying so, rather than throwing.

  4. Re-run the Part 1 experiment — num_predict: 60 — and confirm it now recovers instead of crashing. Watch the cap climb in the retry log.

  5. Add a test. The honest unit to test is the decision, not the call: a small function that takes done_reason and a cap and returns what to do next is pure, fast, and needs no Ollama — which keeps the repo's testing rule intact.
