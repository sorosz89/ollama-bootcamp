Structured output

Everything needed to get schema-valid JSON out of a local model, and the exact boundary of what that buys you.

Checked 26 Oct 2026 · Ollama 0.6.x · ollama-js 0.6.4 · zod 4

The guarantee boundary

GuaranteedNot guaranteed
Output matches the schema's shape, token by tokenThe values are true, sane, or internally consistent
No preamble, apology, or markdown fenceThat generation finishes — truncation yields unparseable JSON
Required fields appear; types are respectedContent quality, if the prompt never asked for JSON
Enum values come from your listSpeed — masking costs per-token time, unparallelised

The call, in TypeScript

import ollama from "ollama";
import { z } from "zod";

const Recipe = z.object({
  title: z.string(),
  servings: z.int().positive(),
  steps: z.array(z.string()),
});

const res = await ollama.chat({
  model: "qwen3.5:9b",
  messages: [
    { role: "system", content: "Answer only in the requested JSON." },
    { role: "user", content: "A gluten-free dinner. Return as JSON." },
  ],
  format: z.toJSONSchema(Recipe),   // schema object, not the string "json"
  options: { temperature: 0.3 },     // low; 0 for maximum determinism
  think: false,                      // thinking models only
});

const recipe = Recipe.parse(JSON.parse(res.message.content));

One Zod schema does both jobs: z.toJSONSchema() produces the constraint sent to the model, and the same object parses the reply into a typed value.

The same call, as curl

curl http://localhost:11434/api/chat -d '{
  "model": "qwen3.5:9b",
  "messages": [{"role": "user", "content": "Name 3 gluten-free grains. Return as JSON."}],
  "stream": false,
  "format": {
    "type": "object",
    "properties": { "grains": { "type": "array", "items": { "type": "string" } } },
    "required": ["grains"]
  }
}'

Options worth knowing

OptionWhereUse
formattop level"json" for loose JSON mode; a schema object for constrained decoding. Always prefer the schema.
options.temperaturenested0.2–0.4 for structured work; 0 when you want the same answer twice.
options.num_ctxnestedContext window. Too small is the usual cause of forgotten history in a long chat.
options.num_predictnestedCap on generated tokens. Too low is the usual cause of truncated JSON.
keep_alivetop levelHow long the model stays resident. Default 5m; "30m" to avoid cold-start pauses.
thinktop levelfalse to skip reasoning tokens on thinking models. Errors on models without the capability.

Symptom → cause

SymptomLikely causeFix
JSON.parse throws on a truncated stringGeneration hit num_predict or ran out of contextRaise num_predict; shrink the schema or the history
Valid JSON, nonsense valuesWorking as designed — the grammar never saw the semanticsVerify in code and feed problems back as a revision turn
Long runs of whitespace or paddingPrompt never asked for JSON, so sampling fell off the likely pathSay "return as JSON" in the prompt as well as setting format
Noticeably slower than unconstrained callsPer-token grammar masking, not parallelisedSimplify the schema; drop fields you do not consume
Fields present but always the same valueTemperature at 0 plus a weak promptRaise to ~0.3, or give the model more to go on

Rule of thumb. If a wrong value would do damage, the schema is not your safeguard — it only decides where the value lands in the object. Write the check.
