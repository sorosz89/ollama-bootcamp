Resilient calls

Every way a model call can end, how to detect it, and what to do about it.

Checked 26 Oct 2026 · Ollama 0.6.x · ollama-js 0.6.4

How a reply ends

done_reasonMeansDo
"stop"The model finished on its own.Parse it. Then verify the contents.
"length"Hit num_predict mid-generation.Do not parse. Raise the cap or shrink the request, then retry.
"unload"The model was unloaded during the request.Retry once; check keep_alive and memory pressure.
throwsServer unreachable, model not pulled, request aborted.Not a retry case. Fail with a message naming the cause.

The order of checks

const res = await ollama.chat({ /* … */ });

// 1. How did it end?
if (res.done_reason === "length") { cap = Math.round(cap * 1.5); continue; }

// 2. Is it syntactically parseable?
let value: T;
try { value = Schema.parse(JSON.parse(res.message.content)); }
catch { continue; }                       // malformed: a retry may help

// 3. Is it actually correct?
const problems = check(value);
if (problems.length === 0) return { kind: "ok", value };

// 4. Is it worth another round?
if (!improving(problems) || attempt === max)
  return { kind: "off-target", value, problems };

history.push(revisionMessage(problems));  // change the request, then loop

Skipping step 1 turns a truncation into a confusing SyntaxError. Skipping step 4 gives you a loop that spins without converging.

Outcomes, as a type

type Outcome<T> =
  | { kind: "ok";         value: T }
  | { kind: "off-target"; value: T; problems: string[] }
  | { kind: "no-answer";  why: string };

Three endings the caller must handle. Running out of attempts is an ordinary result, not an exception — an exception escapes to wherever someone remembered to catch it, which is rarely where the decision belongs.

Rules for retrying

RuleBecause
Every retry must change an input.An identical request that failed deterministically will fail identically. Raise the cap, add the problems, shrink the schema — or do not retry.
Send all problems at once.Constraints are coupled. One at a time lets the loop oscillate — fixing protein breaks calories, fixing calories breaks fat.
Stop when not improving.Measure distance to target each round. Stalled progress means another round will not help; a fixed attempt count is superstition by comparison.
Never release a wrong value silently.If you print a result that failed verification, print what failed and by how much alongside it.

Feedback that works

// Weak
"The macros are wrong."

// Strong — field, actual, target, in the model's own units
"protein per serving is 38 g, target 45 g."

Caps worth setting

SettingGuidance
num_predictMeasure your typical reply, then set comfortably above it. A Recipe measured 482 tokens here; a deeply nested schema blew past 1,200.
Max attemptsThree is a reasonable ceiling, but prefer stopping on stalled progress — it usually stops sooner, and for a reason you can print.
Cap growth×1.5 per truncation. Jumping straight to a huge cap risks a runaway generation holding the model's only parallel slot.

The one-line version. Check how it ended, then whether it parsed, then whether it is right — and make every retry change something. Collapsing any of those three into the others is where the bugs live.
