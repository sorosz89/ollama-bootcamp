Performance & diagnostics

Reading the timing receipt, the two rates, and the short list of things that actually make a local model slow.

Checked 26 Oct 2026 · Ollama 0.6.x · figures from a 24 GB Apple Silicon Mac running qwen3.5:9b

The two rates

Prefill (prompt eval)Decode (eval)
Does whatReads your promptWrites the reply
Parallel?Yes — whole prompt at onceNo — strictly one token at a time
Grows withPrompt length (history!)Reply length

Timing fields (all nanoseconds)

tokens/sec  =  eval_count / eval_duration * 1e9        # decode rate (the usual quote)
prefill/sec =  prompt_eval_count / prompt_eval_duration * 1e9
FieldMeans
load_durationModel load. Non-zero = cold start, not slowness.
prompt_eval_countPrompt tokens — i.e. how much history you resend each turn.
prompt_eval_durationTime evaluating uncached prompt tokens. Unchanged prefixes are nearly free.
eval_count / eval_durationReply tokens and the time to generate them.
total_durationWall clock for the whole call.

Only returned when "stream": false. Measure with node assets/bench.ts --cold --repeat 2 "your prompt".

Reading ollama ps

NAME          ID              SIZE     PROCESSOR    CONTEXT    RUNNER    UNTIL
qwen3.5:9b    d63f830f28d5    7.7 GB   100% GPU     4096       mlx       4 minutes from now
ColumnRead it as
SIZELive footprint: weights + KV cache. Grows with context actually used, not with the file on disk.
PROCESSORThe one that matters. 100% GPU is healthy; any CPU share means it did not fit and you are off the cliff.
CONTEXTThe configured window. Defaults by VRAM: <24 GiB → 4k, 24–48 GiB → 32k, ≥48 GiB → 256k. Measured here: a 48,050-token prompt still ran, still recalled its system prompt, while this column read 4096. Treat it as the default, not a proven ceiling — and verify on your own runner.
UNTILWhen it unloads. Default 5 minutes idle.

Symptom → cause

SymptomCheckCause and fix
First reply after a pause is slow, rest are fineload_durationModel unloaded after 5 min idle. Set keep_alive: "30m", or -1 to pin it.
Everything is an order of magnitude slowollama ps → PROCESSORSpilling to CPU. Smaller model, smaller context, or free memory.
Long delay before the first token, then fineprompt_eval_countPrefill on a long history. Trim or reset the conversation.
Gradually slower over a long chat sessionprompt_eval_count growing, SIZE climbingHistory compounding. Decide a trimming policy rather than letting it grow.
Benchmark numbers look terribleload_duration > 0You benchmarked a cold run. Discard the first call, always.
Replies truncate mid-JSONeval_count vs num_predictHit the generation cap. See Structured output.

Knobs

KnobWhereEffect
keep_aliveper requestResidency. Duration string, seconds, -1 to pin, 0 to unload immediately.
OLLAMA_KEEP_ALIVEserver envSame, for every model. Per-request keep_alive overrides it.
OLLAMA_CONTEXT_LENGTHserver envOLLAMA_CONTEXT_LENGTH=64000 ollama serve. Costs memory; agents and coding tools want ≥ 64k.
options.num_ctxper requestPer-call context window.
ollama stop <model>CLIFree the memory now.
ollama run <model> --verboseCLIPrints the same timing stats after each interactive reply.

Benchmarking discipline. Discard the first call (cold load). Change one variable at a time. Quote prefill and decode separately, and say whether the prompt was cached — a repeated prompt measured ~7× faster prefill here, which is enough to fake any result you like.
